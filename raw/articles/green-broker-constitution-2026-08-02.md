# Конституция проекта: Telegram-бот для продажи растений (Green Broker)

## 1. Роли и участники
- **Разработчик (Пользователь):** Единоличный исполнитель, который выполняет весь объем работ по созданию Telegram-бота.
- **ИИ-ассистент (Я):** Помощник разработчика. Моя задача — анализировать вводные данные, формировать спецификации и помогать с написанием кода по технологии Spec-Driven Development.
- **Заказчик/Стейкхолдеры:** Лица из сферы ландшафтного дизайна, строительных компаний и частные клиенты (покупатели растений), а также менеджеры и владельцы садовых центров/питомников (поставщики растений).

## 2. Основная цель проекта
Разработать полнофункциональный Telegram-бот для питомников растений, который автоматизирует рутинный процесс продаж. Бот ДОЛЖЕН предоставлять функцию удобного внесения карточек товара через телефон для продавцов и главное — мгновенно формировать коммерческие предложения (КП) по запросу (текст, фото, файл PDF, Word, Excel) заказчиков через бот с учетом актуальных складских остатков по каждому питомнику/садовому центру. 
**Глобальная цель:** Развернуть экосистему (маркетплейс в Telegram) из множества ботов (один питомник/садовый центр = один бот) для объединения всего рынка озеленения, сбора аналитики и стандартизации продаж.

## 3. Ключевые принципы разработки (Правила)
- **Стек технологий:** Проект реализуется на Python (современный фреймворк `aiogram 3.x`). База данных для MVP — `SQLite` (с таблицами пользователей, каталога, заказов и «виртуальной» корзины), с прицелом на легкую миграцию в `PostgreSQL` при масштабировании до маркетплейса. Архитектура должна быть упакована в `Docker`, что позволит разворачивать бота на классическом VPS (виртуальном сервере).
- **Поэтапный запуск (MVP):** Разработка ДОЛЖНА четко разделять два пользовательских пути: B2B (профессионалы) и B2C (частники). Для MVP (первая фаза) абсолютным приоритетом ДОЛЖНА быть реализация функционала для ландшафтников — парсинг неструктурированных заявок (текст, Excel, PDF) с помощью ИИ, сборка их в "скрытую/виртуальную" корзину и мгновенная выдача КП. Классический визуальный интернет-магазин с картинками и кнопками "в корзину" (B2C) выносится во вторую фазу проекта.
- **Хранение медиа:** Для обеспечения масштабируемости, надежности и программного доступа, фотографии товаров, сгенерированные PDF (КП) и документы ДОЛЖНЫ загружаться в S3-совместимое объектное хранилище (например, Yandex Object Storage, AWS S3, Selectel, MinIO). В базе данных хранятся прямые ссылки на объекты в S3 (поддержка до 2-х фото на товар).
- **Бизнес-процессы (КП и Оформление):** Бот ДОЛЖЕН автоматически генерировать детализированное сообщение (чек/КП) с шапкой питомника, геометкой и ссылкой на менеджера сразу после оформления корзины.
- **Мини-CRM:** Все данные о заказчике (имя, телефон, ник, сумма, номер заказа) ДОЛЖНЫ сохраняться в отдельную таблицу заказов одной строкой для последующего легкого экспорта во внешние CRM-системы (например, Bitrix).
- **Управление остатками:** База остатков ДОЛЖНА управляться менеджерами напрямую через Telegram-интерфейс (команды типа `/ostatki`). Допускается заказ "в минус", но с обязательным подтверждением и корректировкой менеджером.
- **Интеграция платежей:** Для реализации модуля подарочных сертификатов ДОЛЖНА использоваться интеграция с ЮKassa (через BotFather) для приема оплат онлайн и выдачи промокодов.
- **Масштабируемость и ИИ (Future Proof):** Архитектура БД и логика бота ДОЛЖНЫ проектироваться с учетом:
    - Будущей интеграции LLM (для консультаций бота 24/7 и автопарсинга списков растений от ландшафтников).
    - Синхронизации со складскими учетными системами (Бизнес Пак, 1С).

## 4. Ограничения и рамки
- Вся документация, спецификации, планы и задачи ДОЛЖНЫ вестись исключительно на русском языке.
- Процесс разработки ДОЛЖЕН быть итеративным по методологии Spec-Driven Development: обновление Конституции -> Спецификация (`spec.md`) -> План реализации (`plan.md`) -> Разбор на задачи (`tasks.md`) -> Реализация.
